# Single-frame flicker: investigation, 2026-10-18

Continuation of `Flicker_video_2026-10-17.md`. Defect not fixed.

## Scenario

`out/dev/flicker-laurence.py` (save copy, route to Laurence, final frame captured every
frame from 31 s). Run wrapper that cleans raw frames and counts flashes:
`~/.claude/jobs/9cdc30a2/tmp/run.sh`. Dark flash: mean brightness ~7; bright: ~133.
Flashes occur in roughly 2–3 of 4 runs, so one clean run proves nothing.

**Warning:** fullscreen 2560×1080 final dumps at 100 FPS cannot reach disk fast enough.
Buffers accumulate in GTT (+8 GB over the cinematic), eventually causing
`amdgpu: Not enough memory for command submission` → device lost.
Do not maximize test windows.

## Established findings

- Upscaler input (finished LDR scene at the display pass) is clean in bad frames.
- Dark frame: all geometry (scene and HUD) occupies only the upper-left quarter at 1:1;
  remainder black. Bright frame: scene layer shifted (−W/2, −H/2), solid background,
  UI intact.
- Display buffer always drawn by one draw (vs 89cda9e4, 2560×1080, scale 1):
  "final pass at native size" hypothesis rejected (`BB_DISPLAY_WATCH=1`).
- Tone-mapping constants (vs 1ea5a07e) unchanged on flash frames (`BB_TRACE_CB`).
- Dark flashes also occur in 0.6-pre1 (2 of 4), so this is old. Bright flashes seen
  only in post-0.6-pre1 builds. 0.5/0.51 do not start in the current environment
  (Python preparation fails); no bisection through those releases.

## Experiments (runs with flashes / total)

| Variant | Result |
|---|---|
| Default | Flashes in most runs |
| `BB_EXP_CONSTRAM_FINISH=1` (every CE dump: stage B catches up, GPU finishes everything) | 0/5 |
| `BB_EXP_CONSTRAM_FINISH=2` (only catch stage B up and submit) | 2/3 |
| `BB_EXP_CONSTRAM_FINISH=3` (wait for GPU on submitted work) | 0/3, but 1/2 on 4 threads and FPS down to 89 |
| `BB_EXP_FLIP_FINISH=1` (GPU finishes frame before flip signal) | 1/6 normal runs (failing run had an FPS drop) |
| `BB_EXP_FLIP_LAG=1` (at most one GPU frame in flight) | 2/5 |
| `BB_CONSTANT_RING_MB=512` (16× constant ring) | 2/4: ring not responsible |
| `BB_DYNAMIC_STATE_ALWAYS=1`, `BB_CONSTRAM_PIPE=0` | Only shift timing (dark ↔ bright) |

Conclusion: flashes disappear only when stage A and the game do not run ahead of the GPU
within a frame. This is a "CPU writes while GPU still reads already submitted work" race,
but the specific write has not been found.

## Checked and clean

- `BB_INPLACE_READ_CHECK=1`: at each CE dump after normal waits, no outstanding GPU
  bindings (shader buffers, paged, vertex, index) overlap its bytes; no outstanding
  GPU writes or textures in its range.
- `BB_DYNSTATE_CHECK=1` (viewport/scissor per command buffer): 0 mismatches,
  but dark flashes did not occur with this check.
- `SceneTargets::CleanupStaleEntries` never fires in the runs.
- `InvalidateMemoryFromGPU` touches only images beginning at the write address.

## Code changes

Fix (retained): `buffer_cache.cpp`, `NoteCommandWriteTick`: small GPU command-stream
writes (192 bytes beside the CE ring each frame) are tracked at 256-byte granularity,
not a 64-KiB page. Previously this forced final-pass constants to be read in place
instead of copied. Did not eliminate flashes.

Diagnostics (all off by default, remove before release):
`BB_DYNSTATE_CHECK`, `BB_TRACE_CB` (`=hash` / `=all`), `BB_TRACE_CB_LIST`,
`BB_GPU_WRITE_WATCH`, `BB_INPLACE_READ_CHECK`, `BB_DISPLAY_WATCH`,
`BB_EXP_CONSTRAM_FINISH`, `BB_EXP_FLIP_FINISH`, `BB_EXP_FLIP_LAG`, `BB_CONSTANT_RING_MB`,
and overnight `BB_DRAW_WATCH`, `BB_DYNAMIC_STATE_ALWAYS`, `BB_EXP_*`, `BB_DUMP_EVERY/ONLY`.
Pre-change source: `~/.claude/jobs/9cdc30a2/tmp/*.orig`.

## 19 October: cause found — occlusion compute overwrites push constants

Dumps before each draw into 0x10791e0000 (`q`; dumping closes the pass, so `q`
can precede draw 1 and draw 2) show the bright-flash frame already shifted
**after draw 1**, the vs 0b0acf50 / ps ccbf44a6 quad.
This draw is clip-disabled (`BB_DISPLAY_WATCH` +
`BB_DISPLAY_WATCH_TARGET=10791e0000`): its shader computes position from push constants,
`(pos * xscale + xoffset) / 8192 - 1`; CPU push is always 1280,1280,-540,540.
Exactly (−W/2, −H/2) means xoffset = yoffset = 0 with correct xscale/yscale:
the first 8 bytes of push constants were overwritten.

Recording order in `Rasterizer::BeginDraw` was `BindResources` (push constants) →
`scheduler.BeginRendering` → `CarrySuspend(false)` → `OcclusionQueries::Suspend` →
`Resolve()`: compute dispatch with `pushConstants {count, num_events}` (8 bytes
at offset 0) → draw. In RADV (and per spec for incompatible layouts), compute and
graphics share push constants, so the draw received integer count/num_events as
float ≈0. `Resolve` is not recorded every pass (requires pending occlusion results
or exhausted slots), explaining isolated frames and dependence on stage A's GPU lead
(`BB_EXP_CONSTRAM_FINISH` changed timing).

Fix: move `BindResources` after `scheduler.BeginRendering` (compute cannot be recorded
inside the pass). This mechanism affects any clip-disabled draw at pass start,
probably also the dark variant (display copy vs 89cda9e4 is clip-disabled too).

Validation (`run.sh`, run to boss, `--move 20`): 6 of 6 runs without bright or dark
flashes (`pc-1`…`pc-6`); before the fix most runs flashed. FPS unchanged.
Remove this investigation's diagnostics before release (list above plus
`BB_DISPLAY_WATCH_TARGET`, `BB_PASS_DUMP_AT`, `BB_TRACE_PIPELINE`,
`BB_TRACE_GPU_INPUTS`, `BB_EXP_*`).
