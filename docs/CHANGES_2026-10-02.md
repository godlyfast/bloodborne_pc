# Changes 2026-10-02 (local, unpublished)

What was done, how to verify it, and what of it is confirmed by measurements. All measurements —
on an RX 7800 XT / RADV; "weak CPU" — the same machine limited by `taskset` to 4 cores / 8 threads.

## Performance and smoothness

### Steam Deck and weak GPUs: the release-0.1 path is the default again

For non-1080p output (720p on the Deck, 1440p, 2160p) the whole game is again rendered at the
preset resolution (a patch at startup), as in 0.1. Live scaling kept post-processing at 1080p and
copied the scene targets back and forth every frame: on the Deck and GTX 1060 that gave 7–8 FPS.

- Path selection — the "On-the-fly resolution change" setting (launcher, menu, `bbport.ini`
  `live_resolution=auto|0|1`, applied after a restart). **Auto** (previously the default; since
  03.10 the default is "off") enables live switching on discrete GPUs with 8+ GB of memory, except
  NVIDIA older than Turing: on an RX 7800 XT resolution and presets change in the menu on the fly
  again, while the Steam Deck and GTX 1060 get the fast path. The decision is written to the log
  (`GPU: … live resolution changes on/off`); `BB_LIVE_RES=0/1` overrides everything.
- With this path, changing the preset, output resolution, or switching to TAA in the menu is done
  via the "Apply and restart the game" button.
- Depth/stencil of the downscaled targets on GPUs without `VK_EXT_shader_stencil_export` (Pascal)
  is full-size again, without the 9-pass copy.

### Ragged frametimes when GPU-bound (NVIDIA)

Two causes, both fixed:

1. Frame presentation (`vkAcquireNextImage`, `vkQueuePresent`) ran on the game's vblank thread.
   When the GPU is loaded, these calls block (especially on NVIDIA), and the game's vblank events
   arrived unevenly. Presentation is now on a separate `bb:Present` thread (`BB_PRESENT_THREAD=0` —
   as before).
2. The GPU command thread ran ahead and hit random resources; flips came in bursts. Now it runs no
   more than `BB_FRAMES_AHEAD` frames ahead of the GPU (default 1; 0 — no limit).

4K without an upscaler, ~78 FPS, slow camera pan (`Frame pacing` in the log, 5 s windows):

| | FPS | frame spread | p99 | frames > 1.5× median |
|---|---|---|---|---|
| before | 79.5 | 9.9 ms | 25.8 ms | ~125 |
| separate present thread | 79.4 | 5.9 ms | 25.0 ms | ~80 |
| + 1 frame ahead | 77.4 | **0.9 ms** | **14.6 ms** | **0** |

On the weak CPU (720p FSR 3 Performance, no cap) the frame-ahead limit does not affect FPS (166 FPS
at 0, 1, and 2), while the separate present thread gave +3.5% (160 → 166 FPS).

A new `Frame pacing:` line in `BB_FRAME_STATS=1`: median, spread, p99, and the number of spikes.

### Shader cache disabled itself permanently (freezes when entering every new area)

At startup the pipeline cache compares the saved `Shader::Profile` with the current one. In
upstream shadPS4, on a mismatch the cache **closes for the entire session** and records nothing;
the profile file stays old, so the cache never works again, and every session recompiles all
shaders. Today the profile changed (a flag for Pascal), and since ~12:16 the cache was off for
every launch — including a run near Ludwig's arena: 64 compilations in 114 ms in the freeze window.

Now an incompatible cache is cleared and rebuilt (one rebuild, as on an update). In the log:
`Pipeline cache isn't compatible with current system: rebuilding it`. Verification: running the
route twice in a row — 241 compilations the first time, 28 the second.

The same freeze when leaving the arena (115 ms, a player's run): besides the compilations —
registration of 1057 textures and loading of 220 MB of images and 245 MB of buffers in a single
frame (page protection 17 ms, residency 10.5 ms, image creation 7.9 ms, the rest is copying). That
part still has to be spread across frames or threads.

### CPU on weak processors

Profile (`perf`, 4 cores / 8 threads, 720p FSR 3 Performance, no cap, walking): ~166 FPS, the limit
is the pipeline's second stage (`bb:DrawRec`, 88–90% busy; the first stage waits on it ~40%). The
second stage's time is smeared across resource binding and draw recording; there is no single hot
spot. For the Deck and Haswell (cores roughly half as fast) this is around 85–100 FPS — above 60,
i.e. the average FPS there is not CPU-bound. The main weak-CPU problem is loading stutters (see
"Tools").

- The Vulkan recording thread chose its spin time from the total number of threads on the machine
  rather than those available to the process: under a core restriction it spun for 200 µs instead
  of 20.
- Waiting on the second stage now also depends on the core count (`BB_PIPE_SPIN_US`); it does not
  affect FPS (166.3–166.8 at 0, 50, and 200 µs) and was kept short for machines with 8 threads.
- Readbacks (Relaxed, protecting faces from vertex "explosions"): in the same scene 166.4 FPS
  versus 166.3 with `BB_READBACKS=0` — they cost nothing, no reason to disable them.

## Stability

### Crash `Guest fault … 0x263b8e7` with the two-stage pipeline

`sceGnmSubmitDone` did not block the game when the command thread had already **parsed** all buffers
(`num_submits == 0`), even though the pipeline's second stage and the deferred fence markers had
not yet written memory. The game freed objects with markers, and the late write corrupted the heap.
A `work_retired` flag was added: the GPU is considered idle only after the pipeline drains and the
markers are written.

Verification: 40 minutes on 4 cores / 8 threads without a crash. The crash is rare (the old build
on my machine also survived 40 minutes), so the only confirmation will be the crash not occurring
on your end.

## Image

- **Sharpening up to 2.0** (launcher, menu). Up to 1 — the upscaler's own RCAS; above — one more
  RCAS pass over the finished frame (FSR 3, FSR 4, FSR 4.1.1, including 720p output on the Deck;
  TAA has its own).
- **Ctrl+click on a menu slider** now lets you type a number (previously the keyboard only erased:
  SDL text input was not passed to the menu).
- **Flickering objects on NVIDIA GTX 10xx (Pascal)** — the coffins on the bridge etc. (shadPS4
  PR #1644 fixes this only on Turing and newer via barycentrics). For NVIDIA GPUs without
  `VK_KHR_fragment_shader_barycentric` the recompiler now multiplies the interpolated value by
  1 + 2⁻¹⁶ before converting to integer: 0.99999994 yields 1 again. Found this trick in 27
  Bloodborne shaders; on AMD with it force-enabled (`BB_INTERP_INT_FIX=1`) the picture is
  identical. **Needs testing on GTX 10xx.** The shader cache will rebuild once for everyone (new
  version).
- **Shader-recompiler fixes from recent shadPS4** (released after the version the port's code was
  taken from): `V_CVT_PK_U8_F32`, `V_BFM_B32`, `V_ALIGNBIT/ALIGNBYTE_B32` (a shift by 32 with zero
  alignment gave an undefined result), SCC carry into `S_ADDC/S_SUBB_U32`, 32-bit literals in
  64-bit numbers, the floating-point mode of compute shaders, P10/P20 selectors on
  `V_INTERP_MOV_F32`. The list is in `gpu/VENDOR.txt`. These instructions occur in depth/shadow
  packing; a connection to the shadow bugs (shadPS4 #4384, #3465) is unconfirmed — check those
  places.
- **TAA.** Tried: blending in tonemapped space, history clipping in YCoCg, variance clipping,
  current-frame reconstruction with a 3×3 filter. Comparing within a single run with on-the-fly
  switching (static camera and panning): no technique gave a win beyond the spread between
  measurements; YCoCg clipping and the 3×3 filter were worse. The default remains the previous
  algorithm; the techniques are available for experiments (`BB_TOGGLE_FILE`, bits 51–54). An
  example of where exactly TAA is unstable is needed (place, what is visible) to fix that
  specifically.

  file-name case does not matter; `Mod/CUSA03173/dvdroot_ps4`, an archive wrapper folder, and mods

## Memory

15 cycles of "Exit Game → Continue" (level reload), 720p FSR 3:

| cycles | process RSS | VRAM |
|---|---|---|
| 0 → 7 | +179 MB | +751 MB |
| 11 → 15 | +8 MB | +15 MB |

The growth flattens: on repeated loads this is cache warm-up (pipelines, textures), not an
unbounded leak. `heaptrack` over 8 such cycles also found no sources growing from load to load (the
large ones are one-time at startup: page table 279 MB, texture-cache pool 92 MB). By design, the
texture cache frees memory only at the VRAM budget. A 40-minute run in one location: RSS ~2.64 GB,
VRAM ~4.29 GB the whole time, no growth. Not tested: a long traverse through many different
locations (cache growth up to the budget is expected there) — that needs a recorded route.

## Test tools

- **Route recording**: `BB_PAD_RECORD=/path/route.txt` — F9 in-game starts and stops
  gamepad/keyboard recording. `BB_PAD_REPLAY=/path/route.txt` plus the word `replay` in
  `BB_PAD_FILE` — playback from the same moment. This way you can run a route once (from the lamp
  near Ludwig to another lamp) and then repeat it in stutter measurements. Playback verified;
  starting a recording with the F9 key cannot be verified automatically — please check it.

  How to record: rest at the lamp near Ludwig, quit to the menu and "Continue" (the character will
  spawn at the lamp), in the launcher under "Extra variables" set
  `BB_PAD_RECORD=/home/<you>/route.txt`, after spawning press F9, run to the other lamp, F9. The
  save will also be needed (the `user/savedata` folder) so that the start is at the same point.
